/*ROUTER*/

public function dispatch(string $method, string $uri): void
    {
        // Відокремлюємо шлях від GET-параметрів (/tasks?page=2 -> /tasks)
        $path = parse_url($uri, PHP_URL_PATH) ?? '/';

        // Нормалізуємо шлях: видаляємо зайвий слеш у кінці, крім кореня
        if ($path !== '/' && str_ends_with($path, '/')) {
            $path = rtrim($path, '/');
        }

        $method = strtoupper($method);

        // Перевіряємо наявність маршруту в таблиці
        if (!isset($this->routes[$method][$path])) {
            $this->handleNotFound($method, $path);
            return;
        }

        [$controllerClass, $actionMethod] = $this->routes[$method][$path];

        if (!class_exists($controllerClass)) {
            throw new RuntimeException("Клас контролера '{$controllerClass}' не знайдено.");
        }

        $controller = new $controllerClass();

        if (!method_exists($controller, $actionMethod)) {
            throw new RuntimeException("Метод '{$actionMethod}' не знайдено в класі '{$controllerClass}'.");
        }

        // Викликаємо відповідну дію контролера
        $controller->$actionMethod();
    }

protected function render(string $view, array $data = []): void
    {
        // Перетворюємо ключі асоціативного масиву на окремі локальні змінні
        extract($data);

        $viewFile = __DIR__ . '/../../views/' . $view . '.php';

        if (!file_exists($viewFile)) {
            throw new RuntimeException("Файл представлення не знайдено: {$viewFile}");
        }

        // Запускаємо буферизацію виводу для отримання згенерованого HTML сторінки
        ob_start();
        require $viewFile;
        $content = ob_get_clean();

        // Підключаємо загальний макет, куди підставляється змінна $content
        $layoutFile = __DIR__ . '/../../views/layouts/main.php';

        if (!file_exists($layoutFile)) {
            throw new RuntimeException("Файл макета не знайдено: {$layoutFile}");
        }

        require $layoutFile;
    }

# Контрольні запитання

1)Опишіть призначення трьох складових архітектурного патерну MVC (Model-View-Controller) та їхню взаємодію у процесі обробки HTTP-запиту.

Model (Модель) описує дані та бізнес-правила. Вона не знає нічого про HTTP-запити й HTML-вивід. Модель відповідає на питання: "Як додати завдання? Як перевірити, чи прострочене воно?"

View (Представлення) — це чистий HTML-шаблон з мінімумом PHP тільки для виведення даних. Воно не робить запитів до бази, не перевіряє $_POST, не перенаправляє. Воно лише виводить те, що йому передали.

Controller (Контролер) — посередник між запитом і відповіддю: 
приймає HTTP-запит ($_GET, $_POST);
викликає потрібні методи Моделі;
передає підготовлені дані у відповідне Представлення.

Браузер надсилає HTTP-запит на сервер, і він потрапляє у Front Controller. Router зіставляє метод і URL із зареєстрованим маршрутом та викликає відповідний метод контролера. Контролер читає дані запиту, звертається до Моделі, отримує від неї дані й передає їх у метод render(). render() підключає потрібне Представлення, вбудовує його в макет, і готовий HTML повертається браузеру.

2)Що таке концепція Front Controller? Які ключові переваги вона надає порівняно зі структурою, де кожній веб-сторінці відповідає окремий PHP-файл?

Front Controller — це єдиний файл (public/index.php), через який проходять усі HTTP-запити. Там підключається автозавантаження, запускається сесія, реєструються маршрути й викликається Router.
Його переваги: спільний код виконується один раз, а не дублюється в кожному файлі, перевірки та обробка 404 знаходяться в одному місці, новий маршрут додається одним рядком у таблицю маршрутів, код і шаблони лежать поза public/, тому недоступні напряму.

3)Чому конфігурація веб-сервера (DocumentRoot) повинна вказувати виключно на каталог public/, а директорії src/ та views/ мають знаходитися за його межами?

Тому що усе, що лежить у DocumentRoot, можна відкрити в браузері за прямим посиланням. Якщо вказати на public/, доступними будуть лише index.php та статика (CSS, JS), а якщо налаштувати DocumentRoot на корінь проєкту, то будь-хто зможе відкрити в браузері /src/, /views/ чи завантажити .env. Це призведе до витоку паролів до бази, вихідного коду та структури застосунку.

4)Як працює компонент Router? Поясніть, навіщо перед пошуком маршруту в таблиці виконувати виклик функції parse_url($uri, PHP_URL_PATH).

Router — це клас, що зберігає таблицю маршрутів і знаходить потрібний обробник для поточного запиту.
Router зберігає таблицю маршрутів у вигляді [метод][шлях] = [контролер, дія]. Методи get() і post() реєструють маршрути. Метод dispatch() приймає HTTP-метод та URI, за допомогою parse_url відокремлює шлях від GET-параметрів, прибирає зайвий слеш у кінці, шукає збіг у таблиці, створює об'єкт контролера і викликає потрібний метод. Якщо маршрут не знайдено, повертається код 404 і сторінка помилки.

$_SERVER['REQUEST_URI'] містить шлях разом з GET-параметрами. У таблиці маршрутів зареєстровано тільки шляхи, тому без очищення такий запит не знайшовся б і користувач отримав би хибну 404. parse_url($uri, PHP_URL_PATH) залишає лише шлях, а параметри контролер бере окремо з $_GET.

5)Поясніть механізм рендерингу представлення за допомогою функцій extract($data) та буферизації виводу ob_start() / ob_get_clean(). Чому цей підхід дозволяє зберегти шаблони «чистими» від бізнес-логіки?

extract($data) перетворює ключі масиву на змінні: з ['tasks' => $arr] виходить $tasks. Шаблон підключається через require всередині render(), тому одразу бачить ці змінні.

ob_start() вмикає буферизацію: увесь вивід шаблону не йде в браузер, а накопичується в пам'яті. ob_get_clean() повертає цей вміст як рядок і очищає буфер. Так HTML сторінки потрапляє в змінну $content, яку можна вставити в базовий макет.

Шаблони залишаються чистими, бо отримують тільки готові змінні й лише виводять їх. Запити до бази, перевірка $_POST і перенаправлення залишаються в контролері та моделі.
